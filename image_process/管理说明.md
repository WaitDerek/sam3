# SAM 3.1 物料检测管理说明

本文档记录本仓库中物料检测配置、运行产物和 Git 提交的管理规范。

## 核心原则

- 各物料必须沉淀可复现的最终最佳检测参数。
- 参数修改必须服务于稳定整体效果，不能只为了局部问题图破坏已有场景。
- 本地输入统一放在 `image_process/dataset/`，检测输出统一放在 `image_process/out/`，确认完整后的正式归档放在 `image_process/changan/<物料名>_<数量>/`。
- `image_process/dataset/`、`image_process/out/`、`image_process/changan/` 都是本地数据目录，不提交 Git；`image_process/dataset/test/` 可作为本地示例保留。

## 最终参数管理

各物料的最终参数以 `image_process/configs/object_segmentation_params.json` 中对应物料的 `parameter_files` 为准。

`parameter_files` 条目应指向 `image_process/configs/materials/<物料名>/<场景>.json` 下的稳定参数文件。参数文件只负责清晰场景，例如：

```text
image_process/configs/materials/副雨刮器/table_view.json
image_process/configs/materials/副雨刮器/bin_view_contact.json
image_process/configs/materials/空调新风口/table_pair_right_repair.json
```

稳定参数文件应包含：

- `name`：稳定、可读的场景名。
- `scene`：场景类型，例如 `single_object`、`container`、`contact`、`manual_repair`。
- `sequence_prefixes`、`min_stem`、`max_stem`：优先使用这些可复现范围字段限定场景。
- `threshold_overrides`：该场景最终确认的阈值。
- `prompts`：该场景最终确认的提示词集合。

物料完成调参后，需要确认：

- `image_process/configs/object_segmentation_params.json` 已引用最终参数文件。
- 不再依赖命令行临时参数作为最终结果来源。
- 不再依赖未记录的本地试验过程解释最终效果。
- `material_detection_registry.json` 记录了关键修复原因、适用范围和不要重跑的边界。

## 临时清单管理

`image_process/configs/*.txt` 用于本地临时检查、补检、回放问题编号，不提交 Git。

如果某次补检只是临时验证，可以保留为本地 txt，并通过 `--image-list` 或参数文件中的 `image_list` 使用。

如果某次补检结果已经成为最终最佳参数的一部分，不应只依赖本地 txt 文件。应优先改成以下形式之一：

- 用 `sequence_prefixes`、`min_stem`、`max_stem` 表达稳定范围。
- 新建明确命名的场景参数 JSON，并在 `material_detection_registry.json` 写明适用图片范围和原因。
- 若必须固定特殊图片，应在 registry 中记录这些 stem 和处理原因，确保审阅者不需要本地 txt 才能理解决策。

## 调参流程

新增或调整物料时按以下流程处理：

- 在 `image_process/configs/materials/<物料名>/` 中新增或复制场景参数 JSON。
- 使用本地 `image_process/dataset/` 和 `image_process/out/` 运行目标范围验证。
- 对比 `image_process/out/<结果目录>/overlays/`、`masks/`、`metadata/`，确认漏检、误检、过大 mask、容器误检都可接受。
- 将稳定参数文件加入 `image_process/configs/object_segmentation_params.json` 的 `parameter_files`。
- 在 `image_process/configs/material_detection_registry.json` 记录关键修复点、阈值原因、适用范围和不要误改的限制。
- 只提交稳定 JSON、代码和说明；不要提交 `image_process/dataset/`、`image_process/out/`、`image_process/configs/*.txt`、`sam3.1_multiplex.pt`。

## 命名规范

- 物料 label 使用纯物料名。
- 数据集编号、批次号、输出编号只放在 `input_dir`、`output_dir` 或内部 material key 中。
- 参数文件名表达场景或修复目的，不使用随手命名。
- 已稳定的修复参数文件不要反复覆盖成临时实验版本；新实验另建文件，确认后再替换引用。

## 验证规范

提交前至少执行：

```bash
python -m py_compile image_process/detect_material_bgr.py image_process/detect_materials.py image_process/run_material_segmentation.py image_process/repair_material_segmentation.py image_process/revert_repair.py image_process/clean_container_fps.py image_process/clean_orphans.py
python image_process/run_material_segmentation.py --help
git diff --check
git ls-files 'image_process/configs/*.txt' sam3.1_multiplex.pt
```

其中 `git ls-files 'image_process/configs/*.txt' sam3.1_multiplex.pt` 应无输出。

如果修改了 JSON 配置，还要确认所有 JSON 可解析：

```bash
python - <<'PY'
import json
from pathlib import Path
for path in [Path('image_process/configs/object_segmentation_params.json'), Path('image_process/configs/material_detection_registry.json'), *Path('image_process/configs/materials').glob('**/*.json')]:
    json.loads(path.read_text(encoding='utf-8'))
print('json ok')
PY
```

如果修改了某个物料的最终参数，还应至少跑该物料的目标场景或代表性样本，并人工检查 overlay、mask、metadata。

## Git 提交规范

提交信息使用 conventional commit 风格，例如：

```text
feat: add material segmentation workflow
chore: ignore local repair image lists
docs: update material management rules
```

提交正文保留必要的 Lore trailer，用于说明约束、拒绝方案和验证结果。至少写清：

- `Constraint:` 影响决策的外部限制。
- `Rejected:` 明确放弃的方案及原因。
- `Tested:` 已完成的验证。
- `Not-tested:` 未验证的风险。
